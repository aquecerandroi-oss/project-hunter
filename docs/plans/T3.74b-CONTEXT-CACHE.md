# Cache de contexto por família — atacar o custo N×M por barra (T3.74b, item 2)

**Status:** desenho para aprovação antes de codar (CLAUDE.md #7: mudança arquitetural no caminho
que decide precisa de doc + aprovação + opinião da Astra antes de implementar).
**Escopo:** `services/strategy-worker/hunter_strategy_worker/` — `context.py`, `consumer.py`, um
módulo novo (`context_cache.py`). **Nada aqui muda uma decisão.** `context_budget.py` não precisa
mudar (§5).

## 1. O problema, medido (T3.74 notes §2c)

`handle_candle` (`consumer.py`) percorre sequencialmente cada versão devida (`versions_for_bar`) e
chama `evaluate_slot` → `build_market_context` (`context.py`), que relê o histórico de candles
inteiro (até `context_minutes(config)`, no máximo `SHADOW_CONTEXT_MAX_MINUTES` = 6000 min) **por
versão**, sem nenhum cache entre versões da mesma família no mesmo (mercado, fechamento de barra).
Com 11 versões ativas agrupadas em famílias (8 `mean_reversion_v1`, por exemplo) e 200 mercados
perpétuos monitorados, uma barra alinhada para toda a família `mean_reversion_v1` custa até 8
leituras completas de contexto para o **mesmo** mercado no **mesmo** instante — candles idênticos,
lidos oito vezes. `docker stats` mediu `hunter-postgres-1` em 178,64 % de CPU com a linha viva
sozinha rodando (T3.74 notes §2c) — nenhum replay concorrente.

## 2. O que não pode mudar (as invariantes desta tarefa)

1. **Cada versão lê exatamente as mesmas linhas que lia antes.** O cache é uma otimização de
   *quantas vezes* o banco é consultado, nunca de *o que* é devolvido.
2. **Não-antecipação intacta**: todo candle servido continua `open_time < source_bar_close`,
   `is_final = true`, na mesma ordem — a mesma garantia que `context.py` já documenta.
3. **Os sete módulos do fecho de `code_ref`** (`packages/core/hunter_core/strategies/{aggregate,
   base, canonical, envelope, indicators, numeric, schema}.py`) **não são tocados.** O cache vive
   inteiramente do lado do worker, atrás da fronteira que `code_ref` já protege.
4. **Provenance inalterada**: `Provenance.context_minutes`, `.bars_in_context`,
   `.available_through` continuam refletindo exatamente o que aquela versão pediu — nunca o que a
   família pediu no agregado.
5. **Elegibilidade (`hours_gate`/`regime_gate`) permanece por versão.** Duas versões da mesma
   família podem ter `eligibility_policy` diferentes (é um campo da *versão*, não da família); o
   cache nunca pode misturar essa parte.

## 3. Por que a leitura de candles é o alvo, e não o contexto inteiro

`build_market_context` faz quatro leituras: candles duráveis (Postgres, `load_candles`, uma janela
de até 6000 min de 1m), `hot_state` tail (Redis, 20 minutos), elegibilidade/regime/horas (depende
da `policy` da **versão**, não pode ser compartilhado sem risco de misturar políticas diferentes) e
derivativos (`load_derivatives`, depende só do mercado e do corte — candidato a um cache futuro,
fora do escopo medido aqui). A leitura de candles é a única que é ao mesmo tempo (a) a mais larga
em volume de dados por natureza (até 6000 linhas contra uma dezena para as outras três) e (b)
idêntica bit a bit entre versões da mesma família que peçam uma janela igual ou menor. **Ressalva
honesta (Astra, revisão do desenho):** T3.74 §2c mediu consultas repetidas e CPU do Postgres em
178,64 % sem isolar quanto desse custo é candles versus as outras três leituras — é um alvo bem
fundamentado, não uma dominância já provada por tempo medido. O benchmark desta tarefa (§7.3) é
quem responde isso com número, não a hipótese.

## 4. O desenho: reaproveitar o `WindowCache` do replay, por família, por barra

`hunter_strategy_worker/replay/candles.py::WindowCache` já resolve este problema exatamente — para
o replay, entre barras consecutivas da mesma versão. A prova de equivalência já existe
(`test_replay_engine.py::TestTheCandleCache`, `cache(...) == load_candles(...)` para cada corte que
a janela visita). É a mesma máquina que este desenho precisa, com o eixo de reuso trocado: em vez
de "entre barras consecutivas da mesma versão", é "entre versões da mesma família no mesmo instante".

**Módulo novo:** `hunter_strategy_worker/context_cache.py`.

```python
async def build_family_readers(
    session: AsyncSession,
    versions: list[ActiveVersion],
    *,
    market: MarketRow,
    bar_close: datetime,
    config: ShadowConfig,
) -> dict[str, CandleReader]:
    """One WindowCache per strategy_key with 2+ due versions this bar."""
```

- Agrupa `versions` (a lista `due` que `handle_candle` já calcula) por `version.strategy_key` — a
  chave que já identifica a família de código (`mean_reversion_v1`, `momentum_v1`, ...). Duas
  `ActiveVersion` com o mesmo `strategy_key` **são** a mesma implementação (`code_ref` liga o
  digest ao módulo, não à linha `strategy_versions`); só os parâmetros congelados diferem.
- Para cada família com **2 ou mais** versões devidas nesta barra: `ceiling = max(v.context_minutes
  (config) for v in members)` — o teto do grupo, não um número novo; é o mesmo
  `context_minutes_for` que cada versão já calcula sozinha. Constrói um `WindowCache` via
  `replay.candles.load_window(session, market=market, window_start=bar_close,
  window_end=bar_close, context_minutes=ceiling)` — com `window_start == window_end == bar_close`
  isso carrega exatamente `[bar_close - ceiling, bar_close)`, uma query.
- Famílias com **1** única versão devida não ganham cache: nada a compartilhar, e construir um
  `WindowCache` para servir a si mesmo só adiciona uma indireção sem reduzir leituras.
- `consumer.handle_candle` passa `candles_reader=family_readers.get(version.strategy_key)` para
  cada chamada de `evaluate_slot` — o parâmetro já existe (T3.19b, para o replay) e já é opcional
  (`None` preserva o caminho de hoje). **Nenhuma mudança em `evaluate_slot`/`decide.py`.**

### Por que isto não muda nenhuma decisão — **para os mesmos dados observados**

`build_market_context` já separa "quantos minutos este contexto pede" (`context_minutes`, por
versão) de "como os candles são obtidos" (`candles_reader`, injetável desde T3.19b). O
`WindowCache.__call__` tem a mesma assinatura de `repo.load_candles` e devolve, provado por teste,
exatamente as mesmas linhas para qualquer `[start, end)` contido na janela pré-carregada. Como
`ceiling ≥ context_minutes(v)` para todo `v` do grupo (é o máximo do próprio grupo), toda chamada
de uma versão-membro sempre cai dentro do `covers()` do cache — nunca há um "quase-hit" incompleto
nem uma queda silenciosa para uma janela menor. Cada versão continua vendo o `context_minutes` que
sempre viu, gravado do jeito que sempre foi (`Provenance.context_minutes` é o do argumento passado
a `build_market_context`, nunca o do cache).

**Ressalva assumida, não escondida (Astra, revisão do desenho, must-fix 1).** A equivalência acima
é condicionada a "os dados não mudaram entre o pré-carregamento e a avaliação da última versão do
grupo" — exatamente a mesma condição que `WindowCache` já assume para o replay
(`replay/candles.py`, "a cache is a snapshot of the series as of the run's start... that is a
property, not a bug"). Sem o cache, cada versão abre sua própria sessão e leria um backfill que
chegasse *entre* duas avaliações da mesma barra; com o cache, uma versão que avalia depois de um
backfill assim ver a mesma foto que a primeira viu. A janela em que isso importa é a duração de um
`handle_candle` (tipicamente sub-segundo a poucos segundos, o que este benchmark também mede) e o
alvo é candles **já fechados** (`is_final = true`, `open_time < source_bar_close`) — um backfill
que os alcance é o caso raro que `censor_after_s`/`gap_recovery_max_s` já tratam como exceção, não
a norma. A prova de equivalência (§7.2) usa uma série gravada e imutável durante o teste — a mesma
disciplina de `test_replay_engine.py::TestSameCodeSameAnswer` — e não afirma equivalência sob
mutação concorrente, que ninguém neste build afirmava ter antes do cache também (duas versões
avaliando a mesma barra em paralelo, hoje, já podem ler candles diferentes se um backfill correr
no meio — o cache estreita essa janela para o pior caso, não a inventa).

**Isolamento de falhas (Astra, must-fix 2).** `build_family_readers` nunca pode deixar uma exceção
escapar para `handle_candle`: hoje uma versão que falha é isolada (`shadow_version_failed_total`,
notas de `handle_candle`) e a barra ainda é reconhecida (ACK). Se o pré-carregamento de uma família
estourar (timeout, conexão), a família cai para `candles_reader=None` (o caminho de hoje, uma
leitura por versão) — nunca aborta as outras famílias nem a barra inteira. É um `try/except` por
família dentro de `build_family_readers`, não por versão: a query já é uma só por família.

## 5. Por que `context_budget.py` não precisa mudar

O teto por família (`ceiling`) é `max()` de números que `ActiveVersion.context_minutes(config)` já
sabe computar — não é um conceito novo, é uma agregação do lado de fora. `context_budget.py`
continua sendo "quanto uma versão, sozinha, precisa" e não sabe (nem precisa saber) que existe
família ou barra. Adicionar a agregação lá acoplaria um módulo puro (`context_budget.py` não lê
IO, não conhece `handle_candle`) a uma decisão de runtime que é do consumidor.

## 6. O que fica de fora deliberadamente

- **`hot_state` tail e `load_derivatives`**: não medidos como o custo dominante em T3.74; ambos
  dependem só de `(market, cut)`, então são candidatos legítimos a um cache igual no futuro, mas
  cachear mais do que o medido é especular sem número (CLAUDE.md #2).
- **Cache entre barras** (como o replay faz): fora de escopo — o processo vivo não sabe qual será
  a próxima barra antes dela chegar, e cachear "para a próxima vez" trocaria memória por uma
  suposição sobre o futuro. O cache vive e morre dentro de uma chamada a `handle_candle`.
- **Famílias entre mercados diferentes**: o `WindowCache` já é por `market_id` (o `__call__`
  original recusa e cai para o banco se `market.id != self._market_id`); `handle_candle` só nunca
  vê dois mercados na mesma chamada, então isso nunca é exercitado — documentado, não implementado.

## 7. Prova pedida (T3.74b)

1. **Unitário**: `build_family_readers` agrupa corretamente por `strategy_key`, ignora grupos de
   1, calcula o teto certo, e o `WindowCache` resultante responde `covers()` para cada membro —
   sem banco (spy nos limites do agrupamento, `WindowCache` já provado em `test_replay_engine.py`).
2. **Integração (Postgres real, testcontainer, 1 arquivo)**: para uma família com N versões
   (parâmetros de janela diferentes) sobre o mesmo mercado/barra, as decisões de **cada** versão
   são byte-idênticas com `candles_reader=None` (caminho de hoje) e com o cache ligado — mesmo
   `Evaluation`, mesmo `ShadowRecord` gravado, mesmo `Provenance.context_minutes` por versão.
3. **Benchmark (mesmo testcontainer, mesma invocação)**: 11 versões × 16 mercados, bars/s antes
   (`candles_reader=None` em todo `evaluate_slot`) vs depois (`build_family_readers` ligado);
   número real reportado nas notas, não estimado. **Resultado (2026-09-10,
   `.claude/state/notes-T3.74b.md` §2.4):** 176 → 32 chamadas a `load_candles` (exatamente o
   desenhado) e uma redução também no tempo total medido localmente. A hipótese é que custos por
   versão que o cache não afeta (`lock_slot`, `load_regime_asof`, `persist_decision`,
   `slots.advance`) limitem o ganho de relógio, mas essa composição não foi decomposta nesta tarefa
   (Astra, revisão final: "esse diagnóstico orienta a próxima otimização para um custo não
   estabelecido") — a redução de contagem de query é a prova do mecanismo; o peso na VPS real
   (Postgres a 178 % de CPU) não foi medido, só argumentado a partir da pressão já registrada em
   T3.74.
