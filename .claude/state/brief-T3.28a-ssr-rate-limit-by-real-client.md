**Owner:** backend-specialist (API) com devops-engineer para o compose/Caddy (mesmo agente, dois escopos). **Reviewers afterwards:** security-reviewer (obrigatório: cabeçalho de IP confiável), code-reviewer. **Do not commit.** **Operational rule: never a background shell; foreground commands with a timeout <= 5 min; testcontainers one file per pytest invocation, one at a time; the tree is shared — never `git stash`/`checkout --`/`restore`/`reset`/`clean`/`commit -a`; add exact files only; do not touch `.env*`; do not stop or recreate local stack containers.** Base: `main` at `385dac6`. ## Measured (local stack, 2026-09-08 13:37Z, design audit)
The audit navigated 7 screens twice within ~25 s. `docker logs docker-web-1`: 24× `Error [ApiError]: Too Many Requests`, `api_request_failed path=/api/v1/me status=429 type=rate-limit-exceeded`, `topbar_market_status_load_failed`, `markets_page_load_failed`; five consecutive screens rendered Next's global "Application error" (`.claude/state/design/2026-09-08/metrics-lab-1440-dark.json` sample text). Cause: `RateLimitMiddleware` keys on `request.client.host` = **the web container's IP** for every server-side fetch (`rate_limit_per_minute = 120`), so the whole site's SSR shares one 120/min bucket; the principal bucket (600/min, after auth) never gets a chance. On the VPS the same topology (web → api inside the compose network) means a few fast clicks by one user, or two users, exhaust the site.

## Deliver
1. **Real client for SSR**: the web forwards the browser's address to the API on every server-side call in a header the API trusts **only from the web container**: uvicorn `--forwarded-allow-ips` (or `ForwardedAllowIps`) set to the compose service name/IP of `web` (and Caddy where relevant), so `request.client.host` is rewritten only when the peer is the web service; forged headers from any other peer stay ignored (keep the docstring's invariant; extend it). Document the trust chain: browser → Caddy (sets X-Forwarded-For) → web (SSR: propagates the same header to the API) → API. If the web's SSR fetch cannot see the browser IP (Next `headers()`), say so and use the principal fallback in 2.
2. **Principal before IP**: when a request carries a verified bearer, the IP bucket is skipped and the principal bucket (600/min) is the only limit — or, if you keep both, the IP bucket for internal peers is `rate_limit_per_minute_internal` (default 6 000/min) so one web container can never starve the site. Choose one; justify in the notes; settings documented in `docs/DEPLOYMENT.md`.
3. Tests: unit for the client-key derivation (peer = web → forwarded IP used; peer = anyone else → forwarded header ignored), the internal/principal precedence; `apps/api/tests/unit/test_rate_limit*.py`.
4. Local proof: rerun `bash .claude/state/tmp/run-design-audit.sh -g "screens 1440"` (Playwright, 7 screens × 2) and show zero `Too Many Requests` in `docker logs docker-web-1 --since 5m`.
